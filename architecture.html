DeskSync — Architecture & System Design

A secure remote desktop: control your laptop (the host) from your phone (the controller) over the internet. Three edges — a Rust desktop agent, a Flutter mobile app, and a Go microservices backend — tied together by WebRTC.

Go · Fiber · PostgreSQL · Redis Rust · Tokio · WebRTC Flutter · Riverpod Coturn STUN/TURN Kubernetes · Helm · k3s

1 · What DeskSync is

DeskSync brokers identity and connection setup through a backend, but the media path is peer-to-peer over WebRTC. The screen is captured on the host, JPEG-encoded, and streamed to the phone over a data channel; touch/keyboard events flow back and are injected on the host.

PrincipleMeaning
Zero-trust mediaThe backend sets up connections but the stream is peer-to-peer; a session key can be derived end-to-end so the server can't read it.
Fail closedNo input executes while a peer is offline; sessions reconnect automatically.
Clean architectureDomain logic sits behind interfaces — Go interfaces, Rust traits, Riverpod providers.
Operable by defaultEvery service exposes /health, /ready, /metrics, JSON logs, correlation IDs.

3 · The three edges in detail

3.1 Backend — Go microservices (backend/)

A Go workspace (go.work), one module per service under services/, shared libraries in pkg/. Only the gateway is public; it verifies JWTs and reverse-proxies internally. Signaling is also reachable (WebSocket).

ServicePortResponsibilityStores
gateway8080TLS ingress, JWT verification, rate limiting, reverse proxyRedis
auth8081Registration, login, Google/GitHub OAuth, JWT + refresh rotationPostgreSQL, Redis
device8082Device registration (public key), presence/heartbeat, revocationPostgreSQL, Redis
session8083Session lifecycle, timeouts, event log, ICE config, issues signaling ticketsPostgreSQL
pairing8084QR + manual-code pairing, trust (codes hashed, TTL, attempt limits)PostgreSQL, Redis
signaling8085WebSocket relay of SDP/ICE + presence; verifies stateless ticketsRedis
relay8086Issues time-limited TURN credentials (HMAC over Coturn secret)—
notification8087Push (FCM) + email deliveryPostgreSQL
monitoring8088Health aggregation / alert hooks—
Cross-service coupling: session issues signaling tickets and signaling verifies them via a shared SIGNALING_TICKET_SECRET (pkg/signalticket). Tickets are stateless HMAC + short TTL, so signaling holds no session state and scales horizontally.

3.2 Desktop agent — Rust Cargo workspace (desktop-agent/)

Headless Tokio daemon split into crates so platform code stays behind traits. Native backends (real capture/input/WebRTC) are enabled with --features native.

CrateRole
coreConfig, types, session-runtime primitives, shared errors
cryptoE2E channel — X25519 → HKDF-SHA256 → AES-256-GCM (wire-compatible with mobile)
captureScreen capture behind a trait; native backend uses xcap
inputKeyboard/mouse/scroll injection (enigo); clipboard (arboard)
transportWebSocket signaling client (tokio-tungstenite + rustls)
mediaJPEG encoder + WebRTC answerer peer; frame chunking lives here
backendREST enrollment client — auth, device registration, pairing (reqwest)
devtoolsAllowlisted dev shortcuts (git/docker/kubectl/helm/ssh) over the control channel
config-uiThe desksync-agent binary: wires everything, hosts session runtime, renders pairing QR

3.3 Mobile — Flutter app (mobile/)

Feature-first: lib/features/<feature>/{presentation, application, domain}, with app/ (routing/theme) and core/ (networking, storage, DI). State via Riverpod, routing via GoRouter, WebRTC via flutter_webrtc. Features: auth, pairing (QR scan), devices (presence), signaling, viewer (WebRTC session + frame render + touch → input mapping).

4 · End-to-end data flows

4.1 Enrollment & auth

Agent and mobile each register a device (public key) via the gateway. Users authenticate (email/password or OAuth) and receive a JWT (+ refresh). Every REST call carries the JWT. The agent heartbeats the device service so the mobile sees it online.

4.3 Session establishment (signaling + WebRTC)

The mobile is the offerer, the agent is the answerer. Signaling only brokers SDP/ICE; media is peer-to-peer.

      M->>SIG: ICE candidate
      SIG->>A: ICE candidate
      A->>SIG: ICE candidate

    end
    Note over M,A: DTLS over STUN/TURN → data channels open
Correctness detail (fixed here): ICE candidates must not be applied before the remote description, and sdpMid must never be null — the Android org.webrtc build crashes otherwise. The mobile serializes signal handling, buffers remote ICE until the answer is applied, and always sends a non-null sdpMid.

4.4 Streaming pipeline (as actually implemented)

The screen is streamed as JPEG frames over a reliable+ordered WebRTC data channel (not an SRTP video track). A whole JPEG exceeds the SCTP max message size, so the agent chunks each frame and the mobile reassembles.

flowchart LR

BGRA frame"] --> ENC["Encode (jpeg-encoder)
~720p ~20fps"]
    ENC --> CHK["Chunk 16 KiB
[frame_id][idx][count][payload]"]
    CHK -->|"'frames' channel
reliable + ordered"| RASM["Reassemble by frame_id

    DEC --> PNT["CustomPainter render
bypasses ImageCache"]
    PNT --> TCH["Touch / key / scroll"]
    TCH -->|"'input' / 'control' channels"| INJ["Input injection (enigo)"]
SafeguardWhy
Skip JPEG encode when no viewer (frames_open())Stale sessions can't CPU-starve the live one
Answer each session at most onceAvoids peer leave/rejoin churn that tore down calls
Keep only the newest decoded frame, dispose the previousBounded memory; no ImageCache blow-up / crash

5 · Deployment

Runs on Kubernetes (k3s in the live Azure environment) via an umbrella Helm chart (helm/desksync). Only the gateway (and signaling) are exposed; Coturn uses host networking with a pinned relay-port range. Values: values.yaml (defaults), values-azure.yaml (live), values-vps.yaml.

7 · How to run (summary)

Full commands, endpoints, credentials location, and troubleshooting live in RUNBOOK.md. At a glance:

# Backend (local dev)
cp .env.example .env
docker compose -f docker/docker-compose.yml up --build

# Backend (Kubernetes)
helm upgrade --install desksync ./helm/desksync -n desksync --create-namespace \
  -f ./helm/desksync/values-azure.yaml

# Desktop agent (the host / Mac being controlled)
cd desktop-agent
cargo build -p desksync-agent --features native
DESKSYNC_EMAIL=... DESKSYNC_PASSWORD=... RUST_LOG=info ./target/debug/desksync-agent
# macOS: grant Screen Recording permission to the launching app

# Mobile app
cd mobile
flutter build apk --release --split-per-abi \
  --dart-define=DESKSYNC_API_BASE_URL=http://<host>:8080 \
  --dart-define=DESKSYNC_SIGNALING_URL=ws://<host>:8085/api/v1/signaling

Flow to connect: start backend → run agent (registers + goes online) → open mobile app, log in → pair once (scan QR) → tap Connect → the phone offers, the agent answers, data channels open, frames stream and touches control the desktop.

DeskSync architecture reference. See ARCHITECTURE.md, RUNBOOK.md, docs/design/, and docs/adr/ for more detail.
